# May 24, 2026 — Diagnostic Deep-Dive: Why ResNet and MNIST Stopped Training

## Background

Two recently-changed test programs (`test/resnet.cpp` for ResNet10 on miniImageNet,
`test/mnist.cpp` for a CNN on MNIST) both produced baffling results: loss stuck at
initial values, validation accuracy near random chance. The MNIST model had previously
achieved 98 % accuracy (loss ~0.02), so something broke it.

The investigation uncovered **six distinct root causes** across four files.

---

## Problem 1: Graph replay reads stale gradients

**File:** `test/resnet.cpp`  
**Symptom:** ResNet loss stuck at ln(100) = 4.6052; `opt:0ms` timing.

```cpp
// BEFORE (broken)
if (use_graph) {
    GPU_CHECK(hipGraphLaunch(graphExec, graph_stream));   // async
    optimizer.step();           // ← reads param.grad_() BEFORE backward finishes!
    (void)hipStreamSynchronize(graph_stream);             // sync happens too late
}
```

The `hipGraphLaunch` is asynchronous on `graph_stream`.  `optimizer.step()` runs
on the default stream and reads `param.grad_()` immediately — before the backward
pass inside the graph has written gradients.  Every optimizer step applies a
zero (or stale) update.  The model cannot learn.

**Fix:** move `hipStreamSynchronize(graph_stream)` **before** `optimizer.step()`:

```cpp
if (use_graph) {
    GPU_CHECK(hipGraphLaunch(graphExec, graph_stream));
    (void)hipStreamSynchronize(graph_stream);             // wait for fwd+loss+bwd
    optimizer.step();           // now reads correct gradients
}
```

## Problem 2: Fused BN+ReLU GPU path drops the autograd chain

**File:** `include/Module.hpp` — `BatchNorm2d::forward_impl()`  
**Symptom:** 18 of 62 ResNet parameters received gradients; the autograd traversal
stopped at every `BatchNorm2d::forward_relu()` call.

The GPU fused `bn_relu_fwd_gpu` kernel creates an output tensor, sets
`requires_grad(true)`, but never creates a `grad_fn_`.  Without a backward node,
the DFS traversal in `Tensor::backward()` cannot proceed through this tensor.
Every `forward_relu()` in the ResNet (one per BasicBlock + one initial) broke
the gradient chain.

**Fix:** bypass the fused path when autograd is active.  Let the decomposed
(operator-based) path build proper backward nodes.

```cpp
// BEFORE: fused path always used on GPU
if (apply_relu && x.device().type == DeviceType::CUDA) {
    Tensor<T> output(x.shape(), x.device());
    bn_relu_fwd_gpu(x, output, mean, var, gamma_, beta_, eps_);
    if (GradMode::is_enabled() && x.requires_grad()) {
        output.set_requires_grad(true);      // ← NO grad_fn_ set!
    }
    return output;
}

// AFTER: only use fused path when gradients are not needed
if (apply_relu && x.device().type == DeviceType::CUDA && !GradMode::is_enabled()) {
    Tensor<T> output(x.shape(), x.device());
    bn_relu_fwd_gpu(x, output, mean, var, gamma_, beta_, eps_);
    return output;
}
```

The decomposed path now runs when `GradMode::is_enabled()`:
```cpp
auto centered = x - mean;                 // SubBackward
auto inv_std  = sqrt(var + eps_);         // SqrtBackward
auto x_hat    = centered / inv_std;       // DivBackward
auto bn_out   = x_hat * view_reshape(gamma_, ...) + view_reshape(beta_, ...);
if (apply_relu) return relu(bn_out);      // ReLUBackward
return bn_out;
```

## Problem 3: BN `reshape()` creates view with separate `grad_`

**File:** `include/Module.hpp` — `BatchNorm2d::forward_impl()`  
**Symptom:** 32 of 62 parameters had gradients after fix #2 — still 30 missing.

The BN computation used `gamma_.reshape({1, C, 1, 1})` which creates a **view**
sharing the same `TensorStorage` but with its own `TensorImpl` — including its
own `grad_` member.  When `MulBackward::apply()` computes the gradient for the
reshape view, it calls `view.accumulate_grad(grad)`, which stores the gradient
in *the view's* `grad_`.  The optimizer later checks `gamma_.grad()` on the
original parameter — which is still empty.

**Fix:** use `view_reshape()` (from `TensorOps.hpp`) which wraps the view with a
`ReshapeBackward` node that routes gradients back to the original tensor:

```cpp
// BEFORE
return x_hat * gamma_.reshape({1, C, 1, 1}) + beta_.reshape({1, C, 1, 1});

// AFTER
return x_hat * view_reshape(gamma_, {1, C, 1, 1})
     + view_reshape(beta_,  {1, C, 1, 1});
```

After this fix: 62/62 parameters receive gradients. ✓

## Problem 4: Winograd weight kernel — local instead of shared memory

**File:** `src/gpu_ops.cpp` — `winograd_weight_kernel()`  
**Symptom:** MNIST loss = 69 (expected ~2.3), Conv2D output completely wrong.

The Winograd weight transform computes `U = G @ w @ G^T` using 16 threads per
(C_out, C_in) pair.  Only threads 0–8 load the nine weight values:

```cpp
T w_flat[9];          // ← LOCAL variable — each thread has its own copy
if (tid < 9) {
    int r = tid / 3, c = tid % 3;
    w_flat[tid] = w[(base * 3 + r) * 3 + c];
}
__syncthreads();      // synchronizes __shared__ only — w_flat is NOT shared!
```

Threads 9–15 have **uninitialized** `w_flat` and compute garbage for U rows 2–3.
The `__syncthreads()` barrier does not synchronize local variables.

Copying U back to CPU confirmed: rows 0–1 correct, rows 2–3 wildly wrong.

**Fix:** declare `w_flat` as `__shared__` so all 16 threads see the loaded values:

```cpp
__shared__ T w_flat[9];
if (tid < 9) {
    int r = tid / 3, c = tid % 3;
    w_flat[tid] = w[(base * 3 + r) * 3 + c];
}
__syncthreads();      // now correctly synchronizes shared memory
```

## Problem 5: Winograd input kernel — wrong B matrix

**File:** `src/gpu_ops.cpp` — `winograd_input_kernel()`  
**Symptom:** Even after fixing #4, Conv2D output still wrong.

The Winograd 2D transform requires `B = B^T^T` (the column transform must be the
transpose of the row transform).  The code used the NNPACK `B` matrix, which is
**not** the transpose of the NNPACK `B^T`:

```
B^T = [[1, 0,-1, 0],    B^T^T = [[1, 0, 0, 0],
      [0, 1, 1, 0],             [0, 1,-1, 1],  ← B[1][3] = +1
      [0,-1, 1, 0],             [-1,1, 1, 0],
      [0, 1, 0,-1]]             [0, 0, 0,-1]]

NNPACK B = [[1, 0, 0, 0],
            [0, 1,-1,-1],  ← B[1][3] = -1  (WRONG for 2D tensor product)
            [-1,1, 1, 0],
            [0, 0, 0,-1]]
```

Verified via Python: `B=B^T^T, A=A^T^T` passes 200/200 random 2D Winograd tests;
`B=NNPACK, A=A^T^T` fails every test at output column 1.

**Fix:** correct the `B[:,3]` sign in the sparse multiply from `-1` to `+1`.

## Problem 6: Winograd input kernel — index-permuted matmul formula

**File:** `src/gpu_ops.cpp` — `winograd_input_kernel()`  
**Symptom:** The original two-stage approach (found before fix #5) computed a
permuted matrix product instead of `V = B^T @ d @ B`.

The original two-stage code computed:
```
mid[i]   = Σₖ B^T[i][k] · d[k][in_col]       // (B^T @ d) for one column
val      = Σₖ mid[k] · B[k][in_row]          // permuted matmul
```

This computes `V_wrong[in_row][in_col] = Σₚ d[p][in_col] · (B@B)[p][in_row]`,
which is **not** equal to `V[in_row][in_col] = Σₚ,ₕ B^T[in_row][p] · d[p][q] · B[q][in_col]`.

**Fix:** rewrite as direct sparse multiply-accumulate exploiting 2×2=4 non-zeros:

```cpp
// B^T[in_row] non-zero columns: p0, p1 with signs s0, s1
// B[:,in_col]  non-zero rows:    q0, q1 with signs t0, t1
val = (s0*t0) * d[p0][q0] + (s0*t1) * d[p0][q1]
    + (s1*t0) * d[p1][q0] + (s1*t1) * d[p1][q1];
```

## Red herrings

- **H2D bottleneck misdiagnosis:** The timing label `h2d:1153ms` in the graph
  path actually measured `hipStreamSynchronize + loss.to(CPU)` — the GPU
  execution time, not data transfer.  Actual `hipMemcpy` was 1–2 ms.
- **Cross-entropy numerical stability:** The fused kernel uses standard
  log-sum-exp and `log(fmax(p, 1e-30f))` — numerically stable.  The NaN
  appearing in val_loss was a downstream effect of Problem 1.
- **"Model learning slowly" analysis:** Was incorrect.  The model genuinely
  was **not** training due to the bugs listed above.
